## Как можно поучаствовать

- **Баги** — через [шаблон баг-репорта](.github/ISSUE_TEMPLATE/bug_report.yml).
- **Идеи и фичи** — через [шаблон feature request](.github/ISSUE_TEMPLATE/feature_request.yml).

- **Код и документация** — см. процесс ниже.
- **Edge-cases OpenRPC** — фрагменты схем, ломающие UI, особенно ценны;
  прикладывайте минимальный JSON, воспроизводящий проблему.

## Настройка разработки

```bash
git clone https://github.com/zerobig/openrpc-playground.git
cd openrpc-playground
npm install
npm run dev
```

Откройте `http://localhost:5173/?spec=<url-к-openrpc.json>` для автозагрузки.

| Команда           | Что делает                                               |
| ----------------- | -------------------------------------------------------- |
| `npm run dev`     | Vite dev-сервер с HMR                                    |
| `npm run build`   | `tsc` type-check, затем `vite build` → `dist/index.html` |
| `npm run preview` | Локальный сервер для `dist/`                             |

## Правила кода

- **TypeScript strict.** Сборка прогоняет `tsc` с `noEmit`; ошибка типов
  роняет сборку. Не ослабляйте `strict: true` в `tsconfig.json` ради
  прохождения PR.
- **Без новых runtime-зависимостей** без обоснования в PR. На выходе —
  единый HTML, всё инлайнится.
- **Без фреймворков.** UI — чистый DOM. Если нужно React/Vue/etc. — это
  отдельный форк.
- **Рендеринг.** Вся разметка строится через tagged template `html\`...\`` и
  монтируется через `render(el, ...)` из `src/view.ts`. Интерполяции
  экранируются автоматически, поэтому **не** вызывайте `escapeHtml()` вручную
  и **никогда** не присваивайте `innerHTML`. Для готового доверенного HTML
  (`$ref`-ссылки, pretty JSON) — только `raw()`, `json()` или `code()`. Текст
  из схемы — недоверенный ввод. Обработчики событий навешиваются после
  `render()` через `querySelector` — сохраняйте этот паттерн, чтобы узлы DOM
  оставались заменяемыми.
- **Состояние** — в `src/state.ts`. Не вводите `let` на уровне модуля вне
  `state.ts` и `i18n/index.ts`.
- **Строки** — через `t('key')` из `src/i18n`. Никаких хардкодных строк
  для пользователя в UI-модулях.
- **CSS** — один файл (`src/style.css`). Используйте существующие
  CSS-переменные.
- **Структура** — UI в `src/ui/`, движок рендеринга в `src/view.ts`, сеть в
  `src/api.ts`, переводы в `src/i18n/`.

## Переводы

Английский словарь (`src/i18n/en.ts`) — источник истины. Любая другая
локаль — это `Record<DictKey, string>`; TypeScript проверяет полноту.

### Улучшить существующий перевод

Редактируйте `src/i18n/ru.ts`. Плейсхолдеры (`{var}`) держите точно как в
`en.ts` — не переводите их.

### Добавить новый язык

1. Скопируйте `src/i18n/en.ts` в `src/i18n/<code>.ts`; переведите значения.
2. Зарегистрируйте в `src/i18n/index.ts`:
   ```ts
   import { de } from './de';
   const dicts: Record<Locale, Record<DictKey, string>> = { en, ru, de };
   export const LOCALES = [/* …, */ { code: 'de', label: 'Deutsch' }];
   ```
   Добавьте `'de'` в union `Locale`.
3. Соберите проект и убедитесь, что `tsc` доволен (нет пропущенных ключей).
4. PR с заголовком `feat(i18n): add German`.

Если можете перевести только часть словаря — всё равно открывайте PR,
помечая непереведённое `TODO`-комментарием. Частичные переводы
приветствуются.

## Коммиты

Проект следует [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(playground): запоминать Authorization на метод
fix(tree): стабильный порядок групп при смене локали
docs(readme): описать параметр ?lang
i18n(ru): уточнить формулировки в панели batch
chore(deps): обновить vite до 5.2.x
```

Scope соответствует области: `ui`, `api`, `i18n`, `build`, `docs`, `deps`
или имени компонента (`tree`, `method`, `playground`). Маленькие
сфокусированные коммиты ревьюить проще.

## Процесс pull request

1. Форкните, создайте ветку от `main` (`feat/…`, `fix/…`, `docs/…`, `i18n/…`).
2. Держите PR маленьким; одно логическое изменение на PR.
3. Локально прогоните `npm run build` — должно пройти.
4. Заполните [шаблон PR](.github/PULL_REQUEST_TEMPLATE.md); сослать на
   issue, если есть.
5. Скриншоты (светлая **и** тёмная тема, или с `?lang=en` и `?lang=ru`)
   очень помогают для UI-изменений.
6. Мейнтейнер посмотрит; отвечайте на комментарии новыми коммитами (не
   делайте force-push во время ревью без просьбы).

## Баг-репорты

Приложите:

- `spec`-URL (или **минимальный** фрагмент OpenRPC JSON, воспроизводящий
  проблему).
- Браузер и ОС.
- Шаги воспроизведения.
- Ожидаемое и фактическое поведение.
- Консоль браузера — сетевые и JS-ошибки крайне полезны.
- Если проблема в Playground — имя метода, JSON параметров (с вырезанными
  секретами) и был ли заполнен `Authorization`.

> Вырезайте токены, пароли и внутренние хостнеймы перед публикацией.
